# Teaching Plan

**Audience:** instructor and teaching assistants  
**Workshop length:** six hours  
**Teaching mode:** live, guided, beginner-friendly

## Audience Assumptions

Teach this as a first digital methods workshop. Assume participants may not know what a folder path, terminal command, Python package, notebook kernel, or code cell is. Avoid treating setup vocabulary as obvious.

The academic level can still be high: participants can discuss corpus representation, philological judgment, dialect politics, and model limitations even while they are learning basic computational gestures.

> **Teaching note:** keep the technical ceiling low enough for beginners, but keep the interpretive questions intellectually serious.

## Workshop Flow

| Stage | Instructor focus | Participant action |
| --- | --- | --- |
| 1 | Welcome, expectations, and reassurance about errors | Open the workshop folder |
| 2 | Repository tour | Identify notebooks, data, setup, and readings |
| 3 | Notebook navigation | Run first cells and observe output |
| 4 | Arabic text basics | Edit one short Arabic string |
| 5 | Tokenization and normalization | Compare raw and processed output |
| 6 | Corpus exploration | Search and count within a small sample |
| 7 | Model demonstration | Interpret predictions cautiously |
| 8 | Bias, power, and reflection | Write and discuss a short response |

## Instructional Approach

- Demonstrate every action before asking participants to do it.
- Narrate the purpose of each code cell before running it.
- Keep code edits small: one changed sentence, query word, or variable at a time.
- Pause after every technical concept for a humanities translation of the concept.
- Invite participants to describe what they see before explaining what the code did.
- Normalize errors as part of method learning.

## Academic Framing

Return to these questions throughout the workshop:

| Question | Use it when discussing |
| --- | --- |
| What has been made machine-readable? | Corpus creation, OCR, metadata, file formats |
| What has been omitted, normalized, or simplified? | Preprocessing, diacritics, punctuation, dialects |
| What level of evidence does this output provide? | Counts, token lists, model predictions |
| How do Arabic morphology, script practices, dialects, and digitization histories shape the result? | Every notebook |

## Active Learning

- Ask participants to type their own Arabic example strings.
- Ask them to predict output before running a cell.
- Show how normalization changes visible text and counts.
- Compare raw and cleaned text frequencies.
- Let pairs choose a query word for a concordance-style search.
- Use reflection prompts to connect tool behavior to scholarly interpretation.

## Accessibility and Pace

- Keep a shared screen visible throughout technical sections.
- Leave commands on screen long enough for copying.
- Avoid switching rapidly between Terminal, browser, and editor.
- Give participants permission to follow conceptually if installation fails.
- Provide a paired option for anyone blocked by local setup.

## Repeated Phrases That Help

| Moment | Suggested phrase |
| --- | --- |
| Before code | “First we will predict what this cell might do.” |
| After output | “What changed on the screen?” |
| After an error | “This is information from the computer, not a failure.” |
| Before interpretation | “What can we claim from this output, and what would require more evidence?” |
